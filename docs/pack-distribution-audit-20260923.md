# 抽卡集中问题复核（2026-09-23）

## 已确认的历史原因

玩家反馈存在真实依据。`p:P43` 是 Juhan。普通卡重标定前（`7c8884e^`），选手卡直接使用 `world.json` 的 `overall` 分金银铜，LPL 的 103 张普通卡中只有 Juhan 一张低于银卡线 72。旧 LPL 包每次选中铜卡档，必定抽出 Juhan；稀有度内等概率并不能解决只有一张候选卡的问题。

使用该 Git 版本完整隔离的 `src` 与 `release-policy.js`，调用真实 `openPack`，与当前版本并排复现。每个种子连续开 667 个 LPL 包，共 2001 张，保底、包内升级与随机数均使用各版本原实现：

| 固定种子 | 旧版 Juhan 张数 | 当前 Juhan 张数 |
| --- | ---: | ---: |
| 12345 | 939 | 21 |
| 54321 | 977 | 20 |
| 99999 | 990 | 25 |
| 42424 | 957 | 19 |
| 77777 | 989 | 22 |
| 合计（各 10005 张） | 4852（48.50%） | 107（1.07%） |

普通卡重标定提交 `7c8884e` 已将 LPL 铜卡池扩至 43 张。原始 world 数据保留不变，实际抽卡使用校准后的卡表。现有库存不会因卡池修复自动减少，`seen` 也包含收信、交易等获得途径，所以不能将单个账户的累计 `seen` 全部认定为抽卡所得。

线上只读匿名汇总也发现了相符的历史痕迹：一位累计 1865 抽的玩家，Juhan 的累计获得次数为 381；另外两位累计 3610、3811 抽的玩家分别为 953、535。前两位可见的近期开包日志有大量旧版 LPL 包记录；1865 抽玩家最近 60 条日志里有 55 条 LPL 包记录，没有十连包记录。日志与累计获得次数都不能完整还原每次抽取来源，因此不能证实反馈所说的“十连包出 300 张”；旧版 LPL 单铜卡的机制已经足以解释数百张重复，而当前十连包需要单独验收。

## 当前实现检查

- 12 种可用包（7 种主包、4 种位置包、彩卡包），分别走 `openPack` 与服务端 `runAction('open')`，每条路径 10 个固定种子账号、每账号约 2000 张，共 480080 张。
- 其中十连包单独覆盖 40 个约 2000 张的账号样本（合计 40000 张）；单账号某张卡的最高次数在直接开包路径为 11、服务端路径为 10。当前样本没有复现 300/2000 的集中情况。
- 普通全池 102 金、190 银、385 铜；LPL 为 25/35/43，LCK 为 35/30/57，其他为 42/125/285。源数组未发现重复卡 ID。
- 40 张彩卡按卡 ID 等权。彩卡包两条路径各抽 20000 张，40 张均出现；每个约 2000 张的样本中，最多同一卡分别为 69、73 张。这个结果不能用来保证真实随机抽取永不出现极端情况。
- 赛区包分别只有该区的彩卡：LPL 13、LCK 15、其他 12。40 张彩卡对应 36 位人物，Faker 有 4 个不同卡 ID，Zeus 有 2 个；按人物合并统计不等于按卡统计。
- 当前 `roll().done()` 保存消耗完成后的 RNG 状态；服务器开包混入 `randomBytes` 生成的种子。后台赠送的是未开包邮件或明确指定卡 ID，没有另一套后台随机抽卡逻辑。
- 未调整现有稀有度概率、保底、卡牌数值或库存；没有对历史账户执行补偿、删卡或重算。

## 防回归

`scripts/check_pack_distribution.ts` 由实际 DeepSeek 调用产出主体，经过人工审查和补正。初稿中错误的全档均匀预期、失败后重置种子回退和错误稀有度名称未采用。

测试按**已抽到的稀有度张数**计算同档每张卡的期望，包含零出现的候选；足够样本时检查单卡标准化偏差和条件卡方偏差。另用“一张 300/2000”的故意偏斜样本验证检测器确实失败。样本不足的自然彩卡不能据此声称已通过均匀性检验，因此另外对六种可出彩卡的普通包各运行 4000 次强制彩卡保底，验证完整候选覆盖与同档分布。

同时检查各大赛区普通档至少 10 张候选、币购与持包的同种子结果一致、存档重放确定性、服务器不同熵产生不同序列、历史下架包不可开启。

验收命令：

```text
npx tsx scripts/check_pack_distribution.ts
npx tsx scripts/check_pack_rng.ts
npx tsx scripts/check_mythic_floor.ts

```

以上均通过。历史复现使用隔离检出进行，未修改工作区生产实现；其生成文件只留在本地审计目录。线上具体账户每一张历史卡的来源仍应结合后台操作记录核对，不能仅凭累计库存倒推。
